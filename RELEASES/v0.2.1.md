**Ship date:** 2026-05-28
**Theme:** Versioned decision lineage

## Context

v0.2.1's scope shifted in flight. The schedule wiring originally forecast for v0.2.1 moved into v0.2.2; v0.2.1 took on the audit-trail upgrade instead, because the next round of depth work needs lineage in place before it can land safely.

v0.2 added the warehouse layer, the regime engine, and a permanent decision record. With those in place the owner could ask "what did the bot decide today?" and get an honest answer. Two questions one level deeper were still expensive: "which research packet drove this specific decision, and under what regime?" and "did the most recent release regress something an earlier release had right?" Both wanted provenance the schema did not yet carry.

v0.2.1 adds that provenance. Every record now carries an identifier linking it to the upstream records that produced it, and every record stamps the release version that wrote it. Historical rows from earlier releases are backfilled under a single labelled cohort so audit queries reach back across versions cleanly.

## Outcomes

**Decisions trace back to their drivers without fuzzy joins.** A new identifier on every row, plus a pointer to the parent record that produced it, lets a single query stitch a decision back to its conviction, its research packet, the macro-regime classification of the day, and the nightly batch that initiated the run. Previously this took a date-and-ticker join that quietly dropped rows that crossed midnight in the wrong timezone.

**Every record carries the code version that wrote it.** A release-version field is stamped on every write the platform makes. Comparing decisions across releases is a where clause, not a forensic reconstruction.

**Historical rows joined the lineage system.** Decisions, research packets, and conviction records from before v0.2.1 are backfilled with stable identifiers under a single labelled cohort. The same lineage query that works against today's data works against the full history.

**The nightly batch has a name.** A new root table records each nightly run with start time, end time, status, and originating trigger. Every downstream record points back to that batch identifier, so a single batch's full footprint, including the records that failed and the records that succeeded, is one query away.

**A lineage view stitches the tree in one read.** A new view joins decisions to their conviction, research packet, macro context, and originating batch. Direct queries by ticker, regime, release version, or trigger source now work end to end without per-table joins.
